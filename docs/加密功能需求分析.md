# 数据库加密功能 · 需求分析

版本：v1.0 ｜ 日期：2026-11-22 ｜ 状态：已评审并实现（F1–F5，2026-11-23 完成）

---

## 一、背景与动机

当前软件的所有账本数据以**明文 SQLite 文件**（`database/*.db`）保存在磁盘上，任何能接触电脑的人（家人、同事、维修人员）都可以用文本编辑器或 SQLite 工具直接查看全部收支记录。收支数据属于高度敏感的个人隐私，用户（尤其是淘宝售卖场景下的买家）会提出"我的账能不能加锁"的需求。

**目标：** 允许用户为指定账本文件加密，没有密码的人无法读取数据；加密不影响软件现有的全部功能。

---

## 二、用户场景与需求描述

### 场景 1：给已有账本加密

用户已有一个使用一段时间的账本（如 `root.db`），希望通过菜单操作为其设置密码，加密后原文件变成密文。

### 场景 2：新建一个加密账本

用户新建账本时可以选择"加密账本"，设置密码后创建；之后每次打开都需要输入密码。

### 场景 3：打开加密账本

用户通过「文件 → 打开」选中一个已加密的 `.db` 文件，软件弹出密码输入框，验证通过后才能载入数据；密码错误给出提示并允许重试。

### 场景 4：解密账本

用户想取消某个账本的加密（如换到一台可信的私人电脑长期使用），通过菜单解密并恢复原样。

### 场景 5：密码修改

用户定期更换密码，或怀疑密码泄露后修改密码。

## 三、功能需求

### 3.1 功能列表

| 编号 | 功能 | 优先级 | 说明 |
|------|------|--------|------|
| F1 | 加密指定数据库 | 高 | 菜单入口，选择目标 .db 文件，设置密码后原地转为密文 |
| F2 | 新建加密账本 | 高 | 「文件 → 新建」时可选加密，创建即密文 |
| F3 | 打开加密账本 | 高 | 打开文件时自动识别是否加密，弹密码框验证 |
| F4 | 解密数据库 | 高 | 输入原密码验证后转回明文 |
| F5 | 修改密码 | 中 | 验证原密码后设置新密码 |
| F6 | 密码强度提示 | 低 | 少于 6 位或纯数字时给出弱密码提示（不强制拦截） |
| F7 | 当前账本一键加密/解密 | 中 | 对当前正在使用的账本直接操作，免去文件选择 |

### 3.2 交互流程（F1 加密）

1. 菜单「文件 → 加密数据库…」（或对当前账本「文件 → 加密当前账本」）；
2. 若目标账本正在被其他窗口使用，提示先关闭或自动切换；
3. 弹出对话框：输入密码 + 确认密码（两次输入不一致报错）；
4. 可选：弱密码提示；
5. 执行加密，进度/完成提示：「加密成功，今后打开此账本需要输入密码」；
6. 若当前打开的就是该账本，加密后保持打开状态，下次启动才需要密码。

### 3.3 打开流程（F3）

1. 「文件 → 打开」选择 `.db` 文件；
2. 软件读取文件头识别加密标记：
   - 明文 → 直接载入（现状不变）；
   - 密文 → 弹出密码输入框；
3. 密码错误 → 提示「密码错误」，允许重试/取消；
4. 连续错误 5 次 → 本次打开操作终止（防暴力穷举的最低限度措施）；
5. 验证通过 → 解密到内存临时文件（或内存数据库）后正常载入。

### 3.4 界面需求

- 密码输入框一律使用掩码显示（`show="•"`）；
- 弹窗风格与现有对话框一致（`_fit_to_content`、Accent 按钮）；
- 菜单项放在「文件」菜单，加密相关项在「保存/另存为」附近。

### 3.5 错误与异常处理

| 情况 | 处理 |
|------|------|
| 密码两次输入不一致 | 提示，留在对话框 |
| 打开密文文件时密码错误 | 提示并可重试，最多 5 次 |
| 密文文件被外部修改/损坏 | 提示「文件已损坏或不是有效的账本文件」，禁止降级为空白账本 |
| 加密过程中断（断电/杀进程） | 先写临时文件再原子替换（rename），避免留下半个文件 |
| 磁盘空间不足 | 加密前检查目标空间 ≥ 原文件 × 1.2 |

## 四、技术方案选型（关键决策）

### 方案 A：整文件 AES 加密（推荐）

用用户密码派生密钥（PBKDF2-HMAC-SHA256，≥60 万次迭代），AES-256-GCM 加密整个 `.db` 文件。

- **优点：**
  - 实现简单，依赖少（`cryptography` 库纯 Python wheel，打包无系统依赖）；
  - 文件头加魔数标记，识别加密与否一行代码；
  - 与现有 SQLite 代码零耦合，数据库层完全不用改；
  - 对 PyInstaller 打包友好（exe 体积略增，无编译风险）。
- **缺点：**
  - 必须整个文件解密到内存/临时文件后才能被 SQLite 打开（个人账本普遍 < 10MB，完全可接受）；
  - 不是"数据库级"细粒度加密（对单机个人软件属过度设计）。

### 方案 B：SQLCipher（数据库级加密）

替换 SQLite 为 SQLCipher，打开数据库时 `PRAGMA key`。

- **优点：** 行业标准方案，按需加解密页，性能最好。
- **缺点：** `pysqlcipher3` 需要系统 libsqlcipher 开发包，Windows 打包极其麻烦；PyInstaller  spec 大改；给淘宝买家分发提高翻车风险。

### 结论

**推荐方案 A。** 本软件是单机个人记账工具，数据量小，"整文件加密"在安全性和实现成本间最平衡；方案 B 留作后续升级路径（接口上把加解密收敛到独立模块，将来替换内部实现不影响其他代码）。

### 4.1 密码与密钥设计

- 仅存密码派生密钥的验证信息：文件头保存 `salt + nonce + 迭代次数 + GCM 认证标签`，**永不存储密码或密钥**；
- 密码校验 = 解密 GCM 成功（认证标签匹配），无需单独存哈希；
- 迭代次数随文件头保存，便于将来提高强度后兼容旧文件。

### 4.2 加解密时的数据通路

- 打开密文账本：解密到**系统临时目录的临时文件**（权限 600），SQLite 打开该临时文件；关闭账本或退出软件时安全删除临时文件（覆写后删除，或至少立即 unlink）。
- 保存：SQLite 正常写临时文件 → 软件退出/关账本时重新加密覆盖原密文。
- 「另存为」：可选择另存为加密或明文格式。

| 模块 | 影响 | 处理 |
|------|------|------|

| 单元测试 | 中 | 新增加解密模块测试（含错误密码、损坏文件、往返一致性） |

## 六、安全边界与风险提示（需向用户明示）

1. **忘记密码 = 数据永久无法恢复**，设计上不提供后门；说明书和加密成功提示中必须明确写出；
2. 加密保护的是"静态文件"，软件运行时数据在内存/临时文件中明文存在——这是所有此类方案的共性，正常场景不构成问题；
3. 防暴力破解依赖密码强度，软件只做弱密码提示，不做强制（过度打扰用户）；
4. 加密文件照常可以被复制/删除，加密不解决备份丢失问题，仍需提醒用户备份 `database` 文件夹。

## 七、验收标准

1. 加密后的 `.db` 用记事本/SQLite 工具打开，看不到任何明文记录（搜索"餐饮""工资"等关键字无结果）；
2. 软件内打开加密账本：密码正确→正常显示数据；密码错误→提示且数据不可见；
3. 加密 → 解密往返后，数据与原明文完全一致（逐字段比对）；
4. 加密账本的新增、编辑、删除、筛选、统计图表、导入导出功能与明文账本表现一致；
5. 加密过程异常中断（模拟杀进程）后，原账本文件仍可正常打开；
6. 现有 78 个单元测试全部通过，新增加密模块测试全部通过。

## 八、已确认决策（2026-11-22 评审）

1. **加密算法方案：方案 A（整文件 AES-256-GCM）**，不采用 SQLCipher；
2. **第一期范围：F1–F4 + F5**（含修改密码）；
3. **密码模型：每本账各自独立密码**，不做主密码；
4. 有未保存修改的当前账本禁用加解密入口，避免数据不一致。
